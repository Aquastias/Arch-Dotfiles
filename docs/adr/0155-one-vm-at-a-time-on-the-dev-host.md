# ADR 0155: One VM at a time on the dev host

## Status
Accepted — implemented. Tightens [ADR 0046] (the matrix parallel cap) and
[ADR 0099] (the host-safety capacity guard).

## Context
The matrix guard ([ADR 0046]) schedules up to `MATRIX_MAX_PARALLEL=3`
VMs, gated on free RAM only. `matrix.sh run --smoke` started two at once
and froze the dev host: RAM fit, CPU and IO did not. A direct `vm.sh`
launch never consulted anything but its own size ([ADR 0099]), so a
second VM could start beside a running `arch-combined`. The owner had
to repeat "one VM at a time, I don't want the host to freeze" across
sessions; a rule only stated in chat is lost at the next one.

## Decision
- **`vm.sh` refuses to boot while another domain runs.** The capacity
  preflight lists running domains other than the target
  (`vm_host_capacity_others_running`) and aborts naming them.
  `VM_ALLOW_PARALLEL=true` opts in.
- **The matrix cap defaults to 1.** `MATRIX_MAX_PARALLEL>1` is the
  opt-in; only then does the scheduler pass `VM_ALLOW_PARALLEL=true` to
  the cells it admits, so its RAM guard still bounds the stack.
- **`vm-agent.sh status|start|stop`** cover the VM power lifecycle, so
  agents stop hand-rolling `virsh list|start|destroy`; `start` keeps
  the same rule.

## Considered alternatives
- **A CPU/load-aware guard.** Rejected: load is a lagging signal (the
  freeze arrives before it shows) and the owner's rule is a count.
- **Agent instructions only.** Rejected: the rule was already said in
  chat and still broken; a guard in the launch path holds for every
  caller.

## Consequences
A full matrix run is serial — slower, never a frozen host. A leftover
running VM blocks the next launch until it is stopped
(`vm-agent.sh stop`) or the opt-in is set.
