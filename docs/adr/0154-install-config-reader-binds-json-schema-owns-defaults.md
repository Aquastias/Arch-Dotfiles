# ADR 0154: Install Config Reader binds JSON; schema owns Install Defaults

## Status
Accepted — implemented (tickets in `.scratch/install-config-reader/`).
Extends [ADR 0015].

## Context
[ADR 0015] made the Install Config schema the single source of truth for
paths and defaults, but its reader read only the `CONFIG_FILE` global. Every
module holding the Effective Config as JSON — the Package Resolver, the
Feature Audit gate, the Guided Installer's state, the VM flows — re-encoded
path + default inline (`jq '.options.bootloader // "systemd-boot"'`): ~80
raw reads across ~30 files, plus jq twins of the derived predicates
(any-ZFS, any-LUKS) in the resolver, the gate and the menu. They drifted:
the resolver's LUKS rule disagreed with the install list, the gate's any-ZFS
missed storage groups, a manual layout validated against the wrong adapter.
The guided menu and seed kept a second copy of 22 defaults.

## Decision
- **Bind.** `install_config_use_json <json>` points every accessor and
  derived predicate at an in-memory Effective Config; `""` returns to
  `CONFIG_FILE`. Binding is process state, so a JSON holder binds inside a
  subshell: `"$(install_config_use_json "$config"; install_config_any_zfs)"`.
  Inside a jq program, pass `install_config_default_object <name>…` in and
  read `// $defaults.<path>`.
- **The schema owns every Install Default** (what an absent field means at
  install). New `number` type (seeded as a JSON number); array defaults list
  elements by comma; `install_config_default`, `install_config_default_object`,
  `install_config_schema_names`. The guided menu and seed derive their
  defaults from it.
- **Guided Launch Presets are not Install Defaults.** Identity, layout
  mode, timezone, desktop, fonts and the Security & Backup Extras baseline
  are what a fresh guided session pre-selects; an absent field installs
  something else. They stay in the seed, never in the schema.
- **Raw Config Read Lint** (`tests/raw-config-reads.sh`, strict): a jq read
  of a schema-owned path followed by `//` and a literal default fails.
  Fields without a schema row have no Install Default to restate and are
  never flagged; `raw-config-ok` exempts JSON that only shares the keys
  (a data pool object, the guest-side probe lib, a VM flow's own fallback).

## Considered alternatives
- **An explicit `<config>` argument on every accessor.** Rejected: ~45
  accessors and every call site change; binding keeps the interface and
  makes the derived predicates work on JSON for free.
- **Temp file + `CONFIG_FILE`** for JSON holders. Rejected: the hand-rolled
  temp-file setup is what the validate entry point (architecture review
  candidate #3) removes.
- **Put the launch presets in the schema.** Rejected: an absent
  `post_install` must stay off at install ([ADR 0041]); a missing hostname
  must still fail.

## Consequences
- A default changes in one row; resolver, gate, menu, seed and install read
  the same rule. Two jq restatements and their parity tests are gone.
- Each bound accessor call costs one jq over the in-memory JSON (plus a
  subshell). Guided preview latency was not measured; watch the menu paths.
- The probe lib runs in the guest without the installer: its two defaults
  stay restated (`raw-config-ok`). Staging FA_CONFIG with the defaults
  filled in would remove them.
- Restated defaults through a jq variable holding a sub-object
  (`$o.swap_size`) escape the lint; listed in ticket 04's notes.
