# ADR 0163: systemd-oomd on fleet hosts, Fedora's memory-pressure defaults

## Status
Accepted — implemented; verified by the desktop Audit Run of 2026-11-03.

## Context
Nothing acted before the kernel OOM killer on the fleet hosts: a runaway app
froze the desktop, worst on the 16 GB laptop where ZFS ARC and games share
RAM ([ADR 0161]). Arch's `systemd` ships `systemd-oomd` but no `ManagedOOM*`
settings, so enabling the service alone monitors nothing (`systemd-oomd(8)`:
each unit must opt in). The Arch Wiki only lists oomd (Improving performance,
userspace OOM daemons) and gives no configuration.

## Decision
- A `systemd-oomd` Host Program, declared in the Fleet Layer
  ([ADR 0157]): enables `systemd-oomd.service` and writes, at `/etc` admin
  paths, a mirror of Fedora's current `systemd-oomd-defaults`:
  `oomd.conf.d` → `DefaultMemoryPressureDurationSec=20s`; `system.slice.d`
  and the user manager's `slice.d` → `ManagedOOMMemoryPressure=kill`,
  `ManagedOOMMemoryPressureLimit=80%`.
- **No swap-exhaustion kill** (`ManagedOOMSwap`): Fedora dropped it from
  its defaults; memory pressure is the signal that precedes a freeze.
- Non-fleet installs (Host Core) stay without it.

## Considered Options
- **earlyoom** — rejected: it decides from free-memory figures that count
  ZFS ARC as used, so on a ZFS root it can kill apps the ARC would have made
  room for. oomd reads PSI pressure, which ARC reclaim does not inflate.
- **Swap kill on `-.slice` + 50% on `user@.service`** — the older Fedora
  shape, rejected for the current one.
- **Enable the service only** — rejected: a silent no-op on Arch.

## Consequences
- Values trace to Fedora's packaging (src.fedoraproject.org rpms/systemd),
  not the Arch Wiki; the program header records it.
- A cgroup is killed after 20 s above 80% pressure; the probe checks oomd
  is active and monitors `/system.slice`.
