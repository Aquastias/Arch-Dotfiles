# Hybrid AMD+NVIDIA GPU hardening

Status: ready-for-agent

Decision of record: **ADR 0053** (auto hybrid AMD+NVIDIA GPU hardening; drop
envycontrol), building on the existing **GPU Resolution** (ADR 0017,
environment-resolution self-contained) and the **Chroot Configuration Module**
sequence that runs `initcpio.sh`. Test realism per ADR 0046 / 0048: this feature
is **not VM-verifiable**, so it lands with pure-core unit tests plus a manual
on-hardware checklist.

Glossary touched (`CONTEXT.md`): new terms **Hybrid Graphics** / **PRIME
Offload** (AMD iGPU drives the panel + compositor, NVIDIA dGPU on-demand),
**GPU Hardening** (the deterministic config set below), **Early KMS** (nvidia
modules in `MODULES=`), **RTD3** (idle dGPU runtime power-off to D3cold). The
**GPU Resolution** entry changes: an `amd`+`nvidia` result no longer adds
`envycontrol`; it now triggers GPU Hardening in the chroot.

## Problem Statement

On a switchable-graphics laptop (Legion 5: AMD iGPU + NVIDIA RTX 3060 dGPU), the
installer detects both vendors via `auto`, installs both driver sets, and pulls
in `envycontrol` — a runtime mode switcher it **never invokes**. Nothing sets
`nvidia-drm.modeset`, loads the NVIDIA stack early, powers the idle dGPU down, or
rebuilds the initramfs when the driver upgrades. The result is the exact race the
operator wants gone: at boot `amdgpu` and `nvidia_drm` both register DRM devices,
and the window where the dGPU is half-initialised (or modeset is off) is when
PRIME offload and suspend/resume break — intermittently, so it reads as a race.
The operator logs into KDE and hits black screens, failed offloads, or broken
resume, with no deterministic config to blame or fix.

## Solution

When GPU Resolution detects **both** `amd` and `nvidia`, the installer applies a
**deterministic hybrid-graphics hardening set** in the chroot instead of leaving
an uninvoked switcher behind. KDE reaches a usable **Wayland** login with the
compositor on the reliable AMD iGPU; the NVIDIA dGPU stays idle (powered down)
until an app is offloaded to it, and suspend/resume is clean. The whole set is
version-controlled and owned by one module — no second tool that can silently
overwrite it — so the hybrid config is reproducible and inspectable rather than
an intermittent mystery.

From the operator's seat: flash, install with `gpu: auto` (or an explicit
`["amd","nvidia"]`), reboot, and log into a working Plasma session with good
battery life and no graphics races — zero manual GPU fiddling.

## User Stories

1. As a Legion 5 operator, I want the installer to auto-detect my AMD iGPU +
   NVIDIA dGPU, so that I don't have to hand-configure hybrid graphics.
2. As an operator, I want to log into KDE on Wayland without a black screen, so
   that the machine is usable on first boot.
3. As an operator, I want the KDE compositor to run on the AMD iGPU, so that the
   login/greeter path never depends on the proprietary NVIDIA stack.
4. As an operator, I want `nvidia-drm.modeset=1` set deterministically, so that
   PRIME offload and Wayland buffer sharing actually work.
5. As an operator, I want the NVIDIA modules loaded early (Early KMS), so that
   there is no window where the dGPU is half-initialised when the display comes
   up.
6. As an operator, I want the idle NVIDIA dGPU to power down (RTD3), so that my
   laptop battery lasts.
7. As an operator, I want `prime-run <app>` to render on the NVIDIA GPU, so that
   I can run games/CUDA on demand.
8. As an operator, I want suspend/resume to return without corruption or a black
   screen, so that closing the lid is safe.
9. As an operator, I want the initramfs rebuilt automatically when the NVIDIA
   driver or kernel upgrades, so that modeset + Early KMS survive updates.
10. As an operator, I want `nouveau` blacklisted, so that it never races the
    proprietary module for the dGPU.
11. As an operator, I want an X11 fallback session available at the greeter, so
    that a Wayland regression doesn't lock me out.
12. As an operator on a single-vendor machine (amd-only, nvidia-only, intel,
    VM), I want the hardening to NOT apply, so that non-hybrid installs are
    unchanged.
13. As an operator, I want the hardening to trigger with no new config field, so
    that `gpu: auto` "just works" on the Legion.
14. As a maintainer, I want the GPU vendors visible in the chroot, so that a
    chroot module can decide whether to harden.
15. As a maintainer, I want the hardening config generated by pure, testable
    functions, so that I can assert the exact emitted text without a VM.
16. As a maintainer, I want `envycontrol` removed from the install, so that the
    version-controlled config is the single source of truth.
17. As a maintainer, I want the GPU module ordered before `initcpio.sh`, so that
    the single `mkinitcpio -P` bakes in MODULES + modprobe.d with no second
    build.
18. As a maintainer, I want a regression test proving `amd`+`nvidia` no longer
    pulls `envycontrol`, so that the drop can't silently revert.
19. As a maintainer, I want the manual on-hardware checklist recorded, so that
    on-Legion acceptance is repeatable.

## Implementation Decisions

- **Trigger — auto-gate on both vendors.** GPU Hardening applies iff the
  resolved GPU vendor list contains **both** `amd` and `nvidia`. No new schema
  field (`environment.gpu_mode` was considered and rejected in ADR 0053). A
  desktop pairing both vendors gets a harmless superset.
- **New chroot module: the GPU Configuration Module.** A new Chroot
  Configuration Module owns the entire hardening set. It follows the established
  pure-core + thin-IO shape of `initcpio.sh`:
  - a pure **gating** predicate over the vendor list (both amd and nvidia →
    harden);
  - pure **text generators**, one per artifact, returning the file/line content
    as strings;
  - a thin IO layer that writes the files, edits `mkinitcpio.conf`, and enables
    the services — skipped when a lib-only sourcing guard is set (as
    `initcpio.sh` does with `INITCPIO_LIB_ONLY`).
- **The hardening set (artifacts):**
  - `modprobe.d` NVIDIA config: `options nvidia_drm modeset=1 fbdev=1`,
    `options nvidia NVreg_PreserveVideoMemoryAllocations=1`,
    `options nvidia NVreg_DynamicPowerManagement=0x02`, `blacklist nouveau`.
  - **Early KMS**: append `nvidia nvidia_modeset nvidia_uvm nvidia_drm` to the
    `MODULES=(...)` line in `/etc/mkinitcpio.conf` (today only `HOOKS` is set).
    The generator takes the existing MODULES content and returns the augmented
    line, idempotently (re-running does not duplicate entries).
  - **RTD3** udev rule: set the dGPU PCI `power/control=auto` on idle so the
    dGPU reaches D3cold.
  - **Suspend/resume**: enable `nvidia-suspend`, `nvidia-resume`,
    `nvidia-hibernate`.
  - **Initramfs regen pacman hook**: rebuild the initramfs on `nvidia*`/`linux*`
    upgrade, named to sort **after** the DKMS hook (e.g. `95-…`) so the module
    is built before the image is regenerated.
- **GPU vendors into install-state.** `install-state.json` gains a `gpu` array,
  written from `ENVIRONMENT_GPU`. The GPU Configuration Module reads it via the
  existing install-state load path. Preserves both the single-vendor and array
  shapes.
- **Ordering.** The GPU Configuration Module runs in `configure.sh` **before**
  `initcpio.sh`, so the artifacts exist when the single `mkinitcpio -P` runs.
  Ordering is load-bearing: after the build would drop Early KMS.
- **Drop envycontrol.** Remove `envycontrol` from the paru package set in GPU
  Resolution. Trade-off (per ADR 0053): loses the one-command runtime switch to
  integrated-only / dGPU-only; changing topology becomes a deliberate reconfig.
- **Session unchanged.** SDDM stays Wayland-only with the existing
  `plasma-x11-session` fallback (compositor on amdgpu makes Wayland the safe
  primary; X11 is the escape hatch). No display-manager changes in this PRD.
- **Driver stack unchanged.** `nvidia-open-dkms` + matching `*-headers` (already
  in the pacstrap set for every selected kernel) build during pacstrap; RTX 3060
  (Ampere) is fully supported by the open module.

## Testing Decisions

Good tests here assert **external behavior** — the exact text/line an operator
would inspect on disk, and the gating decision — never the private helper
structure. Prior art: `tests/` coverage of `initcpio.sh`'s pure helpers
(`_initcpio_hooks_line`, `_initcpio_udev_override`) sourced under a lib-only
guard, and `environment.sh`'s `_gpu_vendor_packages` / `_resolve_env_gpu`.

Modules tested (all three chosen with the developer):

1. **GPU Configuration Module — pure generators + gating.** Assert
   `_gpu_should_harden` returns true only for a vendor list containing both amd
   and nvidia (false for `[amd]`, `[nvidia]`, `[intel]`, `[vm]`, empty). Assert
   the exact emitted text of the modprobe config, the augmented MODULES line
   (adds the four nvidia modules, idempotent on re-run), the udev rule, and the
   pacman hook.
2. **install-state `gpu` round-trip.** Assert `ENVIRONMENT_GPU` →
   `install-state.json` `gpu` → chroot read is lossless for both the array
   (`[amd,nvidia]`) and single-vendor shapes.
3. **envycontrol drop regression.** Assert resolving `[amd,nvidia]` yields a
   `GPU_PARU_PACKAGES` with **no** `envycontrol`.

The full end-to-end hybrid behavior is **not** VM-testable and is covered by the
manual on-Legion checklist in Out of Scope / Further Notes.

## Out of Scope

- Automated end-to-end verification of the running hybrid stack. No VM emulates
  the proprietary NVIDIA driver or hybrid hardware; the Combination Matrix can
  only prove "installs without error." On-hardware behavior is verified
  manually.
- An `environment.gpu_mode` schema knob and the integrated-only / dGPU-only
  topologies. Rejected in ADR 0053; hybrid is the committed default.
- Display-manager / session changes beyond what already exists (SDDM Wayland +
  `plasma-x11-session` fallback).
- Kernel-cmdline modeset plumbing through the Bootloader Adapters (modprobe.d
  was chosen instead).
- Non-NVIDIA hybrid combinations (e.g. Intel iGPU + NVIDIA) — only the
  amd+nvidia gate is in scope; the Intel path already resolves its own drivers.

## Further Notes

**Manual on-Legion acceptance checklist** (run after first boot into KDE):

- `cat /sys/module/nvidia_drm/parameters/modeset` → `Y`.
- `prime-run glxinfo | grep "OpenGL renderer"` → reports the NVIDIA GPU.
- Idle dGPU reaches D3cold: `cat /sys/bus/pci/devices/<dgpu>/power_state` →
  `D3cold` (and `power/runtime_status` → `suspended`).
- Suspend then resume → returns to Plasma with no black screen, no corruption.
- Reboot after a `nvidia*`/`linux*` upgrade → modeset still `Y` (regen hook
  fired).

The trigger reuses the existing `auto` detection path — on the Legion, `auto`
already resolves to `[amd,nvidia]`, so `hosts/laptop/profile.jsonc` needs no
change.
